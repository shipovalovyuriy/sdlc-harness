# Software Factory (bb plugin)

AIRD discovery и delivery как отдельный раздел bb.

## Установка

Плагин опирается на скиллы и роли AIRD из [sdlc-harness](https://github.com/shipovalovyuriy/sdlc-harness):

```sh
git clone https://github.com/shipovalovyuriy/sdlc-harness.git && cd sdlc-harness
./scripts/install.sh --all --bb-plugin
```

Только плагин: `bb plugin install "git:https://github.com/shipovalovyuriy/sdlc-harness.git@^0.1.0" --subdirectory plugins/software-factory --tag-prefix software-factory/`.
Релизы — теги `software-factory/vX.Y.Z`; bb собирает плагин при установке.

- **Проекты → AIRD.** Проекты — это проекты bb. В каждой папке проекта (корень и
  добавленные подпапки) читаются пакеты `.agent/aird/<slug>/`.
- **AIRD.** Статус и стадия из `STATE.md`, граф стадий discovery → delivery,
  воркордеры (`workorders/`) графом зависимостей по волнам, фиксы и находки
  (`fix-workorders/`, `finding-notes/`), разметка «баг / не баг», гейты из
  `08-quality-gates.md` со статусом из отчётов `10-*-verification.md` (можно
  задать вручную), схема Риски → Гейты → DoD, блокеры, находки ревью,
  артефакты, коммиты ветки `aird/<slug>`. Воркордеры — три вида: майндмап
  (AIRD → волны → WO → фиксы), граф зависимостей и таблица. На стадиях и
  воркордерах видно, какие агенты работают сейчас; клик открывает сессию
  агента прямо в панели (встроенный чат треда).
- **Worktree.** Каждый AIRD работает в своей git worktree на ветке
  `aird/<slug>` (по умолчанию `~/.aird-worktrees/<репозиторий>/<slug>`,
  настройка плагина «Папка для worktree AIRD»). Все треды AIRD — оркестраторы
  и агенты — используют одно bb-окружение этой worktree. Worktree не
  удаляется при архивации тредов. Незакоммиченный пакет из основного checkout
  копируется в неё один раз. Папка вне git работает без worktree (с пометкой).
- **Рабочее пространство из нескольких репозиториев** (папка сама не в git,
  внутри — свои репозитории, пакет в `.agent`). Discovery работает прямо в
  папке: код он не меняет. При запуске delivery плагин собирает копию
  пространства в `~/.aird-worktrees/<папка>/<slug>`: репозитории из
  `allowed_write_paths` воркордеров — git worktree на `aird/<slug>`, всё
  остальное (включая `.agent` с пакетом) — ссылки на основную папку. Пути из
  пакета работают без изменений, checkout'ы пользователя и их ветки не
  трогаются. Новые репозитории из следующих волн добавляются при следующем
  запуске. Слепая приёмка и коммиты считаются по копиям репозиториев;
  для нескольких изменяемых репозиториев набор живёт в отдельном репозитории
  приёмки, база волны — коммит каждого из них, а проверка на базе получает копию
  пространства, где каждый репозиторий стоит на своём базовом коммите.
- **Запуск.** «Создать AIRD» и кнопки Discovery / Delivery создают тред
  `aird-discovery-loop · <slug>` / `aird-delivery-loop · <slug>` в выбранной
  папке. Субагентов скилла оркестратор запускает инструментом `sf_spawn_agent`:
  каждый — отдельный дочерний тред с названием роли (`product-analyst`,
  `architect`, `qa`, `backend-worker`, …), на модели и effort роли из
  `~/.claude/agents/<role>.md` и со списком её скиллов. Результаты забирает
  `sf_wait_agents`. Следующий шаг, который прямо продолжает работу агента, идёт в его же тред через
  `sf_continue_agent` — агент не изучает всё заново; при большом контексте агента (от 300 тыс. токенов или 60%)
  Factory откажет, и оркестратор запустит свежего. До повторного запуска исполнителя
  или debugger того же воркордера Factory проверяет, есть ли свободный небольшой
  агент на той же модели. Для продолжения предлагает `sf_continue_agent`, а для
  отдельной подзадачи принимает `freshReason` с причиной нового контекста.
  Агент после сигнала бюджета продолжаться не может: остаток получает свежий
  воркер по существующей progress-записке. В «Где мы» видно «N новых · M продолжений».
- **Расход.** На обзоре AIRD таблица по моделям разделяет свежий ввод, чтение и
  запись кеша, вывод и суммарное время работы агентов. Учитываются исходные треды
  после переключения на резерв. Исторические вложенные Claude-агенты учитываются
  по отдельным локальным логам сообщений, с дедупликацией; недоступные логи и
  счётчики явно помечаются. Это обработанные токены, включая повторный кеш,
  а не стоимость или расход подписки: тарифов и весов моделей в лимите нет.
- **Материалы.** К AIRD можно приложить скриншоты, макеты и документы: при
  создании (перетащить, вставить ⌘V, выбрать) и позже в обзоре AIRD. Файлы
  лежат в `inputs/` пакета. Оркестратор получает их нативно в первом
  сообщении, агент — те, что названы в его брифе; остальные перечислены путями.
  Файлы, добавленные позже, можно сразу отправить работающему оркестратору.
- **Рабочие каталоги.** Код AIRD — собственный локальный клон (`git clone --local`)
  на ветке `aird/<slug>`, не worktree: git-данные лежат внутри папки AIRD, и
  агент в песочнице может коммитить. Пакет тоже внутри неё (в рабочем
  пространстве из нескольких репозиториев незакоммиченный пакет переносится
  туда, а старый путь становится ссылкой). Перед запуском оркестратора Factory
  проверяет три места — код, git-данные, пакет — и отказывает с понятным
  списком, если что-то вне папки или без права записи; старые worktree
  переводит в клоны сама. Ветку в репозиторий пользователя отправляет Factory.
  `bb software-factory layout <aird> [--prepare]`.
- **Этапы и сессия — операции Factory.** `sf_transition` переводит этапы
  delivery строго по порядку, проверяет результаты этапа и пишет `status` и
  `transitions` в STATE.md и событие в журнал Factory; расхождение файла и
  журнала видно в «Где мы». `sf_slice_begin` перед каждым срезом проверяет
  сессию, срезы этого треда-оркестратора (лимит 6; новый оркестратор начинает с нуля, передавший работу больше срезов не начинает) и заполнение контекста (70% —
  граница, 60% — срез отдаётся worker; без измерения пишет «н/д» и держит
  лимит срезов); `sf_handoff` записывает передачу и запускает свежую сессию,
  счётчик сбрасывается только с её первым срезом.
- **Расход и лимиты.** У каждого агента видно, сколько токенов он потратил
  (каждый шаг заново отправляет весь накопленный контекст); в «Где мы» — сумма
  по провайдерам и последнее сообщение провайдера о лимите подписки
  («в норме», «близко», «исчерпан», время сброса). Бриф каждого агента учит читать
  кусками. Воркер delivery получает разделы из `docs_to_read` своего воркордера
  прямо в брифе и не открывает документы пакета целиком; после ~100 действий
  Factory один раз просит его закоммитить зелёное и записать остаток в
  `evidence/<WO>-progress.md`. Встроенные субагенты провайдера оркестратору
  запрещены: Factory их не видит и не учитывает.
- **Секреты проекта.** Кнопка «Секреты» у проекта (и в диалоге запуска AIRD):
  вход в приложение для живых проверок (`AIRD_APP_URL`, `AIRD_APP_LOGIN`,
  `AIRD_APP_PASSWORD`) и любые другие переменные; «Вставить списком» принимает сразу много строк
  `KEY=value` / `KEY: value` (как в .env или YAML), комментарий над ключом становится описанием. Значения уходят в
  переменные окружения проекта bb (зашифрованы, назад не читаются, то же в
  настройках проекта bb) и доходят до каждого следующего хода агентов во всех
  worktree. Агенты получают в инструкциях только имена и описание и подставляют
  значения через окружение; без секретов они просят их добавить через
  `sf_ask_user`, а не в чате.
- **Модели и роли.** Провайдер (все доступные в bb: Claude Code, Codex, …),
  модель и effort для оркестраторов discovery/delivery и каждой роли.
  Умолчания — из твоих файлов: `~/.claude/agents/*.md`, `~/.codex/agents/*.toml`,
  `~/.claude/settings.json`, `~/.codex/config.toml`. Роль без своего выбора
  наследует провайдера оркестратора и берёт модель/effort/промпт/скиллы из
  файла роли этого провайдера.
- **Запасная модель.** В карточке роли и каждого оркестратора можно выбрать
  один запасной провайдер, модель и effort. По умолчанию резерв выключен.
  При ошибке лимита Factory переключает задачу сразу; при перегрузке,
  обрыве соединения или внутренней ошибке — после двух повторов через 5 и
  10 секунд. Внутри провайдера сохраняется тред; между провайдерами создаётся
  связанная сессия в той же рабочей среде с полным брифом и последними
  событиями предыдущей сессии. Старый процесс останавливается. Ожидание и
  продолжение по прежнему ID следуют за новой сессией, а список считает её
  частью того же агента; история моделей доступна в деталях агента.
  Текущая задача остаётся на запасной модели; новый агент начинает с основной.
  Общий лимит аккаунта может затрагивать несколько его моделей: в таком
  случае нужен другой провайдер. Factory сохраняет решения в базе и
  согласует повторы с Provider Retry. Если результат передачи после сбоя
  нельзя подтвердить, она просит проверить сессии через инбокс вместо
  повторного запуска. Ошибки авторизации, оплаты, бюджета, политик и
  неизвестные ошибки требуют решения пользователя. Недоступный резерв тоже
  останавливает автоматические переключения. Передача не сбрасывает лимит
  срезов оркестратора и не нарушает независимость test-author и исполнителя.
- **Слепая приёмка.** Сценарии «дано → действие → ожидаемое» берутся из
  `09-dod.md` (`### Acceptance Scenarios`). Тесты пишет `test-author` в
  отдельной worktree `aird/<slug>-acceptance`, по умолчанию на другом
  провайдере, не видя реализации. Плагин сам гоняет набор
  (`acceptance/<slug>/run.sh`, результаты в `results.json`) и отдаёт
  оркестратору только вердикты «ожидалось / получено». test-author коммитит
  набор и регистрирует его (`sf_register_suite`): Factory хранит папку набора,
  commit, базу волны и рабочую копию реализации и запускает ровно их; если
  набор не зарегистрирован, изменён или не найден — это «проблема запуска», а
  не результат 0/N. `bb software-factory acceptance <aird> status|register|run [--baseline]`. Вкладка «Приёмка»:
  гейт, сценарии, проверка «красного» на базе, DoD без сценария, прогоны и лог.
- **Вопросы агентов.** Инбокс всего, чего агенты ждут от пользователя:
  карточки `sf_ask_user` (вопрос, варианты с последствиями, рекомендация,
  свой ответ), нативные вопросы и запросы разрешений провайдера, вопросы
  текстом в формате интервью. Блок на главной, страница «Вопросы агентов»,
  вкладка «Вопросы» в AIRD, бейдж в меню; та же карточка — форма в треде.
  История решений сохраняется.
- **Самоулучшение AIRD.** Метрики из `~/.agent/aird-metrics` (history.jsonl,
  improvement-backlog.md, evals/), сигналы правила «повторилось дважды».

## Разработка

```sh
npm install
npx tsc --noEmit -p .
bb plugin build
bb plugin install . --yes   # один раз; дальше bb plugin reload software-factory
```

Код: `server.ts` (RPC, инструменты агентов, запуск тредов), `src/aird.ts`
(разбор пакетов), `src/git.ts` (коммиты), `src/agents.ts` (роли),
`src/ui/*` (страница).

Ограничения: читаются только папки на машине сервера bb; статусы гейтов и
закрытие старых фиксов выводятся эвристически из отчётов и STATE.md.


Проверка изменений (Node.js 25 или новее): `node --import ./tests/resolve-typescript.mjs --test tests/*.test.ts`, затем `npx tsc --noEmit` и `bb plugin build`.
Регрессионные тесты используют временные репозитории и изолированную базу SDK; живые треды агентов не запускаются.
Приёмка требует закоммиченный набор и базу до первого среза каждой волны. Изменение набора требует нового Red-first на сохранённой базе; будущие волны не блокируют текущую.

### Политика эффективности 2

Новые исполнители delivery получают предупреждение при 60 действиях либо свежем
контексте 120 тыс./40% окна, checkpoint — при 80 действиях либо 160 тыс./50%.
Это пилотные значения; работающие старые треды сохраняют прежний лимит 100 действий.
Неизвестное/устаревшее измерение не считается нулём: остаётся контроль действий.
Предупреждение хранится в БД и не повторяется после reload. При ошибке отправки
следующая проверка повторит попытку.

После сигнала агент сохраняет `evidence/<WO>-progress.md`. YAML frontmatter:
`checkpoint_source` (thread id), `checkpoint_revision` (строка),
`checkpoint_dirty_paths`, `checkpoint_completed`, `checkpoint_remaining`,
`checkpoint_checks` (списки строк). Checks содержит команды и результаты либо
явное объяснение, почему проверки не выполнены. Коммит только с разрешения пользователя.
После двух минут Factory может остановить ещё работающий тред, если записка
полная и свежая. Остановка считается подтверждённой только по статусу SDK.
Без полной записки новый исполнитель не запускается: нельзя потерять остаток работы.

Пересекающиеся/неизвестные области записи не запускаются параллельно даже с
`freshReason`. Передача сохраняется до вызова spawn; потерянный ответ восстанавливается
по метаданным созданного треда. Если преемник не найден, повтор остаётся заблокированным,
а не создаёт ещё одного писателя. Встроенные субагенты не заменяют эту передачу.

Новые пакеты используют `efficiency_policy: 2`, явные `risk_flags` и `profile_reason`.
Lite не допускает риски security/migration/schema/multi_service/external_unknown,
а public_contract/cross_layer требуют минимум standard. Старые пакеты не мигрируются
автоматически. Обязательные runtime и независимые проверки сохраняются.

Результат сценария с `phase: "preparation"` блокирует доказательство: такое падение
не доказывает ни дефект продукта, ни red-first. После двух одинаковых ошибок подготовки
нужна правка набора либо `sf_run_acceptance({ retryReason: "что исправлено в окружении" })`.
Assertions не переклассифицируются по свободному тексту. Полная финальная приёмка остаётся
обязательной; текущая проверка commit/scope/dirty revision сохранена, нового механизма
автоматического пропуска произвольных команд нет.

В обзоре календарное время всех попыток отделено от объединения интервалов завершённых
ходов и суммы времени агентов. Интервал хода включает ожидания инструментов и не является
чистым временем генерации. Принятие требует записанного перехода `complete`; неполные
счётчики явно отмечаются. Эти показатели не доказывают экономию без сопоставимых принятых задач.

Для приёмки policy 2 заполняются `verification_inputs` (относительные пути файлов
конфигурации/зависимостей от корня workspace, максимум 32 файла по 1 МБ) и
`verification_environment` (версия фактического окружения). Factory добавляет их
хеш и команды quality gates к существующей идентичности scope/suite/target.
Отсутствующий вход блокирует проверку; изменение делает старое доказательство
устаревшим. Это консервативная проверка актуальности, не автоматический кеш
произвольных тестовых команд. Внешнее изменчивое состояние требует свежей проверки.
